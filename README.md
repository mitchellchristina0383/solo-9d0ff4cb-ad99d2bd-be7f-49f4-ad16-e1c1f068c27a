# 回执对账试跑页（外存左连接算子）

回执表大到放不进内存时，仍然要找出“哪些扣款没收到回执”，并且每条扣款都要
配出**所有**匹配回执。本服务用 Flask 做一个试跑页，背后是一个**外存
（disk-based）左连接算子**：两份 CSV 各自只顺序读一遍，内存中被缓存的输入
记录数有硬上限（≥ 2，可在页面设置），单个交易号的回执再多也能在限额内跑完。

## 快速开始（Docker Compose）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

也可以本地直接跑（依赖只有 Flask）：

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
RECON_DATA_DIR=./data flask --app app run --port 8000
# 或： gunicorn --workers 1 --threads 8 --bind 0.0.0.0:8000 wsgi:app
```

## 输入与输出

两份 CSV 都需要表头 `row_no,txn_id`（行号可自定义为字符串，交易号可为空）：

```
row_no,txn_id
D1,A-100
D2,A-101
```

结果 CSV：

```
debit_row_no,receipt_row_no
D1,R10
D1,R12
D2,
```

* 一条扣款有几条匹配回执，就输出几行（笛卡尔配对）。
* `receipt_row_no` 为空，只会在**整份回执表都查完、确实没有匹配**时出现
  ——它是真左外连接的空值，不是“还没查到”。
* 交易号为空的行不参与配对：空交易号的扣款永远配不到回执，空交易号的回执
  在接收入桶阶段就被跳过（页面上有计数）。

## 算子如何做到外存 + 有界内存

`app/external_join.py` 实现的是一个“先分桶到磁盘、再流式探测”的哈希连接：

1. **回执遍历一次**：顺序读回执 CSV，按 `sha256(txn_id)` 前缀把非空交易号
   的回执追加到磁盘分桶文件（`buckets/<2位散列>/<32位散列>.bucket`）。
   LRU 只同时打开 32 个追加句柄，因此交易号再多也不会耗尽文件描述符。此阶段
   内存中最多只驻留 1 条输入记录。
2. **扣款遍历一次**：顺序读扣款 CSV，对每条扣款按同一哈希找到分桶文件并流式
   比对，命中即写出 `(扣款行号, 回执行号)`。把回执按 `limit-1` 条为一组暂存后
   整组比对，使“同时缓存的输入记录数”真正以配置的上限为界，峰值会被记录并显示。
   分桶用流式读取，所以**单个交易号的回执数超过上限时，仍然在上限内跑完**。
3. 账务由 `_RecordBudget` 统一记账：任何一处多缓存一条都会立刻抛错，而不是
   悄悄超限；页面显示的“实际缓存峰值”就是这个计数器的最大值。

任意时刻驻留的输入记录 = 1 条当前扣款 + 最多 `limit-1` 条回执。分桶文件名、
句柄等都是簿记信息，不随数据量增长（没有按交易号建的内存索引）。

## 中间文件与失败处理

* 所有中间文件都写在本次任务的私有工作目录 `jobs/<id>/work/recon-*/` 下，
  结束时 `shutil.rmtree` 清除。
* 结果先写 `result.csv.part`，`flush` + `fsync` 后 `os.replace` 原子改名。
  **下载接口只在 `result.csv` 已存在且任务成功时返回 200**，否则 409，因此
  不会下载到半份结果。
* 任一临时写失败（真实 I/O 错误，或页面上的“故障注入”模拟）都会：
  1. 抛 `SpillWriteError`，任务置为 `failed` 并在页面显示原因；
  2. 删除 `.part` 文件；
  3. 删除整个工作目录。
  页面同时显示“本次遗留中间文件：0 个”。

## 页面上的自测入口

* **缓存上限**：任意 ≥ 2 的整数。
* **临时盘故障注入**：填 `N` 表示第 N+1 次中间写入失败，用来在页面上复现
  “报错 + 清理”，无需真的把磁盘写满。

## 测试

```bash
pip install -r requirements.txt pytest
python3 -m pytest tests -q
```

覆盖：全量配对、无回执留空、空交易号、超上限热点交易号、不同上限结果一致、
每个输入文件只打开一次、真实 `OSError` 与注入故障的清理、畸形 CSV、
上传/下载/409 语义、并发任务等。

内存与吞吐的可复现实验：

```bash
python3 scripts/bench_memory.py /tmp/recon-bench --debits 600000 --receipts 400000 --hot 100000 --limit 2
```

## 已知限制（未完成项）

* 任务登记在**单进程内存**中（gunicorn 固定 1 worker）。进程重启后，正在跑的
  任务会丢失，`/api/jobs/<id>` 返回 404；磁盘上的旧任务目录按 24h 保留期清理。
* 没有做用户鉴权、限流；这是试跑页，不要直接暴露到公网。
* 结果 CSV 会完整落在磁盘上，没有做流式下载；超大结果受数据卷容量限制。
* 分桶按交易号哈希，若某个交易号本身的桶极端巨大，读它仍然是顺序流式（内存
  有界），但耗时与该桶大小成正比。
